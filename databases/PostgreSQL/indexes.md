# Типы индексов PostgreSQL

## Основные моменты

- PostgreSQL предлагает **6 встроенных типов индексов** + расширение **bloom**
- Каждый использует разный алгоритм, подходящий для разных типов запросов
- **B-tree — индекс по умолчанию** при выполнении `CREATE INDEX`
- Другие типы выбираются с помощью ключевого слова `USING`:
  `CREATE INDEX name ON table USING HASH (column)`

## Типы индексов — Обзор

| Индекс      | Когда использовать                                                                    | Почему                                                                                  | Операторы           |
|-------------|---------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|---------------------|
| **B-Tree**  | Общего назначения — равенство и диапазон на сортируемых данных                        | Самый универсальный, поддерживает `LIKE 'foo%'`, `BETWEEN`, `IN`, `IS NULL`, сортировку | `< <= = >= >`       |
| **Hash**    | Только простые проверки на равенство                                                  | Компактнее B-tree для чистых проверок равенства                                         | `=`                 |
| **GiST**    | Геометрические/пространственные данные, полнотекстовый поиск, поиск ближайших соседей | Гибкая инфраструктура, поддерживающая множество стратегий                               | `<< >> @> <@ && ~=` |
| **SP-GiST** | Несбалансированные структуры — квадродеревья, k-d деревья, префиксные деревья         | Для данных, естественно делящихся на непересекающиеся области                           | `<< >> ~= <@`       |
| **GIN**     | Массивы, составные значения, полнотекстовый поиск                                     | Инвертированный индекс, хранит запись для каждого компонента значения                   | `<@ @> = &&`        |
| **BRIN**    | Очень большие таблицы с физически упорядоченными данными                              | Крайне компактный, хранит только min/max для каждого диапазона блоков                   | `< <= = >= >`       |

## Типы индексов — Подробно

### B-Tree (Сбалансированное дерево)

**Когда использовать:** Общего назначения — запросы на равенство и диапазон на сортируемых данных

**Почему:** Самый универсальный, поддерживает `LIKE 'foo%'`, `BETWEEN`, `IN`, `IS NULL`, сортировку

**Операторы:** `< <= = >= >`

**Пример:** Интернет-магазин, поиск товаров по цене в диапазоне:

```sql
CREATE INDEX idx_price ON products (price);
SELECT * FROM products WHERE price BETWEEN 100 AND 500;
```

### Hash (Хэш-индекс)

**Когда использовать:** Только простые проверки на равенство

**Почему:** Проще и компактнее B-tree для чистых проверок равенства, хранит 32-битный хэш-код
значения

**Операторы:** только `=`

**Пример:** Поиск пользователя по точному email:

```sql
CREATE INDEX idx_email ON users USING HASH (email);
SELECT * FROM users WHERE email = 'user@example.com';
```

### GiST (Обобщённое дерево поиска — Generalized Search Tree)

**Когда использовать:** Геометрические/пространственные данные, полнотекстовый поиск, поиск
ближайших соседей

**Почему:** Гибкая инфраструктура, поддерживающая множество стратегий индексирования

**Операторы:** `<< >> @> <@ && ~=` и др.

**Пример:** Поиск 10 ближайших кафе к заданной точке на карте:

```sql
CREATE INDEX idx_location ON places USING GIST (location);
SELECT * FROM places ORDER BY location <-> point '(55.75, 37.61)' LIMIT 10;
```

### SP-GiST (Пространственно-разделённое обобщённое дерево поиска — Space-Partitioned Generalized Search Tree)

**Когда использовать:** Несбалансированные структуры данных — квадродеревья, k-d деревья, префиксные
деревья (tries)

**Почему:** Хорошо подходит для разделённых/кластеризованных пространственных данных, где данные
естественно делятся на непересекающиеся области

**Операторы:** `<< >> ~= <@` и др.

**Пример:** Поиск всех точек в заданном квадранте координатной плоскости:

```sql
CREATE INDEX idx_point ON locations USING SPGIST (point);
SELECT * FROM locations WHERE point <@ box '((0,0),(100,100))';
```

### GIN (Обобщённый инвертированный индекс — Generalized Inverted Index)

**Когда использовать:** Массивы, составные значения, полнотекстовый поиск

**Почему:** Инвертированный индекс — хранит отдельную запись для каждого компонента значения,
отлично подходит для запросов типа "содержит"

**Операторы:** `<@ @> = &&`

**Пример:** Поиск всех статей, содержащих определённые теги:

```sql
CREATE INDEX idx_tags ON articles USING GIN (tags);
SELECT * FROM articles WHERE tags @> ARRAY['postgresql', 'indexes'];
```

### BRIN (Индекс диапазона блоков — Block Range INdex)

**Когда использовать:** Очень большие таблицы, где данные **физически упорядочены**

**Почему:** Крайне компактный — хранит только минимальное и максимальное значение для каждого
диапазона блоков

**Операторы:** `< <= = >= >`

**Пример:** Логи сервера с временными метками — данные naturally записываются в хронологическом
порядке:

```sql
CREATE INDEX idx_created_at ON server_logs USING BRIN (created_at);
SELECT * FROM server_logs WHERE created_at >= '2024-01-01';
```

## Ключевые отличия

| Индекс      | Главная особенность                                     |
|-------------|---------------------------------------------------------|
| **B-Tree**  | Универсальный, подходит для большинства случаев         |
| **Hash**    | Только `=`, но компактнее для точного поиска            |
| **GiST**    | Гибкий, для пространственных и сложных данных           |
| **SP-GiST** | Как GiST, но для несбалансированных структур            |
| **GIN**     | Лучший выбор для массивов и полнотекстового поиска      |
| **BRIN**    | Самый лёгкий, только для физически упорядоченных данных |

### Когда выбрать GiST

* Данные распределены неравномерно
* Данные могут перекрываться (полигоны, диапазоны)
* Нужна максимальная гибкость — больше готовых классов операторов
* Работаете с PostGIS и пространственными данными в геоинформатике
* Нужен поиск ближайших соседей на сложных данных

### Когда выбрать SP-GiST

* Данные распределены равномерно
* Данные не перекрываются
* Работаете с точками (не полигонами) в 2D/3D пространстве
* Нужен быстрый поиск по префиксу строк
* Данные естественно делятся на чёткие непересекающиеся области

### Когда использовать GIN

* Колонка содержит массивы и нужны запросы на вхождение
* Нужен полнотекстовый поиск
* Данные типа jsonb и нужен поиск по ключам/значениям
* Таблица читается намного чаще, чем пишется
* Нужна максимальная скорость именно на операциях @>, <@, &&

**Коротко**: GIN — это словарь наоборот : не "строка → её содержимое", а "элемент → список строк,
где он встречается". Это делает поиск по содержимому составных значений очень быстрым, но за счёт
более медленной записи и большего размера индекса. Идеален для массивов, JSON и полнотекстового
поиска при преобладании операций чтения.

### Когда использовать BRIN

BRIN эффективен только когда значения колонки коррелируют с физическим порядком строк. Это главное
условие.

**Коротко**: BRIN — это грубый, но очень дешёвый индекс. Он не знает, где именно находится
конкретная строка, но знает, в каких блоках она точно не находится . За счёт этого он отсекает
большие куски таблицы и читает только нужные блоки. Работает блестяще на последовательно растущих
данных — логах, временных рядах, хронологических таблицах. На хаотично распределённых данных
бесполезен.
